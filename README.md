# System Architecture

The system architecture can be divided into two main parts: **Sensor Data Simulator** and **Sensor Data Processing Architecture Simulator**. Below is the detailed description of each module involved, along with the technologies used.

## 1. Sensor Data Simulator

### 1.1 `prediction-frontend`
This is the front-end where the user can input the necessary parameters for the sensor data simulation. The form (see **Figure 1** below) allows the user to provide information such as the sensor name, the unit of measurement, and parameters for the ARIMA model, such as P, D, and Q, as well as configure the number of predictions and the time interval between them. The front-end also allows the user to select a file to upload.

**Technology Used:** React.js

![Figure 1 - Front-end Form](file-FT1jEPksAsipEeG4i6rNDF.png)

### 1.2 `config-service`
This service is responsible for communication between the front-end and the prediction services. It receives the user parameters and sends them to the appropriate prediction service.

**Technology Used:** Spring Boot

### 1.3 `prediction-service`
This is a Python (Flask) service that uses the ARIMA model to make predictions based on the provided data. It processes the data and returns the results to the subsequent systems.

**Technology Used:** Python, Flask, ARIMA

### 1.4 `data-handler`
The `data-handler` service consumes the data generated by the `prediction-service` and allows users to view and update the stored prediction data.

**Technology Used:** Spring Boot

## 2. Sensor Data Processing Architecture Simulator

### 2.1 **Indoor Part**

### 2.1.1 `production-service`
This service is responsible for sending the prediction data to the `productionQueue`, which makes it available for further processing.

**Technology Used:** Spring Boot

### 2.1.2 `gateway-capturer`
The `gateway-capturer` consumes the `productionQueue` and dynamically starts the required number of `capture-services`. The data is balanced across these services using a round-robin mechanism.

**Technology Used:** Spring Boot

### 2.1.3 `Capture-service`
The `capture-service` performs the initial processing of the data. It sends the data to the `sensorDataCaptured` queue and also collects performance metrics, sending them to the `metrics` queue.

**Technology Used:** Spring Boot

### 2.2 **Outdoor Part**

### 2.2.1 `gateway-processor`
The `gateway-processor` consumes the `sensorDataCaptured` queue and starts the required number of `processor-services`. It uses a balancer to distribute the messages across these services.

**Technology Used:** Spring Boot

### 2.2.2 `processor-service`
This service performs heavy data processing. It uses three native C services (aggregator, compressor, and filter) to handle the data. After processing, the data is sent to the `sensorDataProcessed` queue. Performance metrics are also collected and sent to the `metrics` queue.

**Technology Used:** Spring Boot, C (for data processing)

### 2.2.3 `core-service`
The `core-service` is responsible for collecting the processed data from the `sensorDataProcessed` queue, storing it in a historical database, and providing endpoints for later consumption.

**Technology Used:** Spring Boot

### 2.3 **Metrics Dashboard**

### 2.3.1 `metrics-dashboard`
The `metrics-dashboard` provides a visual interface for monitoring the performance metrics of the services. It allows the user to view CPU usage, memory usage, and other dynamically collected metrics.

**Technology Used:** React.js, Chart.js

## Data Flow

### General Flow

1. The **Sensor Data Simulator** (including `prediction-frontend`, `config-service`, and `prediction-service`) receives the user parameters and generates sensor data.
2. The **Sensor Data Processing Architecture Simulator** processes the generated data, starting with the **Indoor Part** using `production-service`, `gateway-capturer`, and `capture-service`.
3. The processed data is then sent to the **Outdoor Part**, where the `gateway-processor` and `processor-service` perform heavier processing, collect performance metrics, and store the processed data.
4. The **core-service** collects the processed data and stores it in a historical database.
5. The **metrics-dashboard** provides the interface to view the performance metrics in real-time.

---

# Technologies Used

- **Frontend (Prediction-Frontend, Metrics-Dashboard):** React.js
- **Backend (Spring Boot):** Java, Spring Boot, RabbitMQ
- **Prediction Models:** Python, Flask, ARIMA, Stochastic Tuning
- **Data Processing:** C (for aggregation, compression, and filtering)
- **Messaging:** RabbitMQ
- **Database:** PostgreSQL
